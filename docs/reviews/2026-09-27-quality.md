# Review of PRs #3–#6

The review examined correctness, idiomatic Rust, readability, and consistency
with the repository's established architecture. The project is pre-launch;
there are no real user digests to migrate. The failures below concern test
fixtures and reproducible new-writing flows, not reported loss of real content.

## Scope and method

Reviewed the changes in dependency order:

| PR | Base | Head | Scope |
|---|---|---|---|
| #3 | `9e6985f` | `69fb102` | Composer, photos, drafts, recovery |
| #4 | `69fb102` | `fcae437` | Places, towns, recent places, slugs |
| #5 | `fcae437` | `def1c24` | Landing pages, search, tags, icons |
| #6 | `def1c24` | `fbd4aa2` | Papercuts and visual harness |

PR #3's base is its merge's first parent, so intervening main changes after
PR #2 are not incorrectly attributed to the composer. GitHub head commits for
the open stack were verified against these local commits.

Three high-effort reviewers covered backend correctness/data integrity, Rust
and maintainability, and browser behavior/test quality. Findings were reconciled
against surrounding code, documented decisions, and the final stack. Reviewers
also checked one another's corrections. Existing accepted limitations and
speculative style preferences were separated from defects.

The pre-#3 history is predominantly earthbasetwo-authored. It establishes the
project's conventions; commit authorship does not prove who wrote each line.

## Engineering assessment

The Rust generally follows the existing design: concrete form/action/error
types, separate parsing and validation, maud rendering, protocol writes in
`publish`, guarded upstream HTTP, and blocking boundaries for SQLite and image
work. The image regression tests exercise actual decoding behavior. There was
no justification for a broad rewrite, a new framework, or cosmetic churn.

The important gaps were state passed between browser and server, failure paths,
resource limits, and tests that did not cover those boundaries. The corrections
keep the server forms authoritative and preserve progressive enhancement.
No migration framework or expanded compatibility layer was introduced.

## Validation

The original PR #3 passed formatting, clippy with warnings denied, and all
365 non-ignored tests. Three live tests were ignored. Its visual run reproduced
the two already documented harness problems at both widths: clipboard reading
and a grantless reconnect session. PR #6 corrects those assertions.

The corrected stack passed `just check` from an isolated build directory:
formatting, clippy with warnings denied, and 392 tests passed, with zero
failures and three live tests intentionally ignored.

The full Chrome harness passed all 157 page views, including desktop and phone
widths, plus two isolated regression groups exercising the actual JavaScript
islands. Those groups cover keyboard expansion/selection, choosing a town
after an initially unknown location, recent Home coordinates, place metadata
in drafts, and delayed search cancellation. The harness also now checks for
JavaScript errors during its interactive exercises. Representative desktop
and phone composer screenshots were inspected.

The browser run used a separate, seeded local atproto network and harness
database. It did not use or modify real user content. An initial shared build
directory produced stale protocol artifacts; the successful final checks and
browser run used the review checkout's own clean application artifacts.

## Remaining limits

- The home page's tag frequencies count the fetched recent page, not the full
  feed. This is a product-scope limitation to clarify before those numbers are
  presented as totals; this review does not add a full-history scan.
- Real-phone behavior, public OAuth, and real-PDS unpublished-blob/preview expiry
  behavior remain deployment checks. The automated network is disposable and
  uses seeded accounts.
- Known calendar-arrow, cross-line selection, HEIC, JPEG truncation, script
  budget, and document/settings design work remains as documented in the wiki.
- Review and passing tests reduce risk; they do not establish that every
  possible input or deployment configuration is correct.
